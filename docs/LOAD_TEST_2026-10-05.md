# Concurrency load test — queueing, RAM and vCPU under the timesheet fix

**Date:** 2026-10-05 · **Endpoint:** `GET /api/v1/admin/reports/shifts?start=2026-07-01&end=2026-09-30`
· **Clients:** 1, 4 and 16 simultaneous · **Verdict:** the fix does not change the *shape* of
queueing (one core of Python serialises every report) — it moves the constant, and that constant
is capacity: **2.5–2.8× the reports per hour on the same vCPU, with 2.5–3.1× lower latency at
every level.** RAM is unchanged (the ceiling is the response bodies); vCPU *utilisation* is
unchanged (saturated either way), only what it buys changes.

This closes the limitation §7 of [PERFORMANCE_AUDIT_2026-10-05.md](PERFORMANCE_AUDIT_2026-10-05.md)
recorded: the audit measured service time through an in-process client, one request at a time.
This measures real uvicorn over loopback, with arrivals that overlap.

**Reproduce:** `python temp/perf_audit/build_load_db.py`, then `serve_variant.py --variant
{after,before}` on two ports, then `python temp/perf_audit/load_runner.py`. Raw per-window
metrics: `temp/perf_audit/load_results.json`.

---

## 1. Method

**Two servers, one difference.** Both run the current working tree through the deployment's own
launcher (`python serve.py --http --port N`, i.e. uvicorn, one process, `limit_concurrency=64`,
access logs on). The "before" server reverts exactly the two components of the timesheet fix,
in-process and before the app is imported: `reports.shift_timesheet_rows` is replaced by the
implementation from git HEAD, and migration 34 is removed from `migrations.MIGRATIONS` with
`SCHEMA_VERSION` back to 33. Its log records the proof it took
(`shift_timesheet_rows from reports_prefix, schema_version=33`), and the two databases were
re-checked **after** the run:

| Server | DB stamp | pairing index | plan for the pairing subquery |
|---|---|---|---|
| after (8791) | 34 | present | `SEARCH prev USING COVERING INDEX idx_attendance_worker_action_id (worker_id=? AND action=? AND id<?)` |
| before (8792) | 33 | absent | `SEARCH prev USING INDEX idx_attendance_worker_ts (worker_id=?)` |

**Identical data.** Both databases are `VACUUM INTO` copies of one harness build — 150 workers,
250 calendar days, 12 sites: 53,405 attendance rows, 155 users, `SUM(id)` equal
(1,430,306,715) on both sides. The real database lives on Railway and was not touched; the
period asked for is a full quarter (~9,900 shifts).

**Client.** `httpx` 0.28.1, one pooled connection per client, barrier-synchronised start, full
response read and discarded (no JSON parse), 300 s timeout. Per window: 60 requests total
(`ceil(60 / clients)` each), preceded by a one-request-per-client warm-up at the same concurrency
and a 2 s settle. Windows are interleaved `after` → `before` at each level, with an
`after_repeat` control at the end.

**Sampling.** Server peak RSS at 20 Hz plus baseline before the window; server and client CPU
seconds from `psutil` across the window, reported as average cores and CPU-ms per request.
Host: 16 logical / 8 physical cores, Windows, Python 3.12.10, SQLite 3.49.1.

### 2.1 Capacity — what one vCPU buys

| Clients | after | before | gain |
|---|---|---|---|
| 1 | 2.001 rps | 0.768 rps | **2.61×** |
| 4 | 2.247 rps | 0.895 rps | **2.51×** |
| 16 | 2.302 rps | 0.824 rps | **2.79×** |

CPU per report falls from 1,230 ms to 465 ms at one client (−62 %) and from 1,245 ms to 497 ms at
sixteen (−60 %). Server utilisation sits at **0.90–1.15 cores at every level for both variants**:
the reports endpoint is a single-core, GIL-bound workload, so concurrency cannot buy throughput —
it only queues. The fix therefore does not reduce *utilisation*, which was already saturated; it
converts the same vCPU into ~2.7× the finished reports.

### 2.2 Queueing — the shape, and the constant

Latency amplification (p50 at 16 clients ÷ p50 at 1 client) is nearly the same on both sides:
**13.1× after, 14.9× before.** Both servers serialise on one core, so the queue grows with the
client count either way; Little's law checks out — 16 clients ÷ 2.30 rps ≈ 7.0 s mean residence,
against a 6.4 s p50 and 0.50 s of service.

What differs is where the amplified curve sits. At 16 clients the before server's median report is
**19.8 seconds** (worst 36.1 s) and the after server's is **6.4 seconds** (worst 12.8 s). An
administrator waiting on a quarter report is looking at either a spinner for twenty seconds or a
table in six — and at 16 simultaneous readers the difference is 0.82 vs 2.30 finished reports per
second, i.e. the backlog drains 2.8× faster.

### 2.3 RAM — unchanged, and not the fix's doing

Peak RSS deltas over baseline: after **+24.3 / +35.3 / +90.9 MB** and before **+20.8 / +37.0 /
+87.7 MB** at 1 / 4 / 16 clients — 1.7–3.5 MB apart at every level. The growth is
concurrency, not code: sixteen simultaneous responses of 5.27 MB decoded JSON is ~84 MB of live
bodies, which is essentially the whole +90 MB. The fix neither adds nor removes memory pressure,
and the wire cost was already handled by gzip (5.27 MB decoded, ~137 KB on the wire).

Baselines (~287–293 MB) are the **local Windows shape**, where `serve.py` runs without
`FACE_ENGINE_PROCESS` and `cv2` is imported into the API process; the deployment's Docker image
defers that to the face child process, and the audit measured the same import at 76.1 MB with the
flag set (§4 of the audit). Ratios transfer; absolute megabytes are hardware-specific.

## 3. Limitations

-  The client shares the host with the server. Client CPU was 0.015–0.38 cores in the measured
  windows (1.25 cores during one 16-client warm-up), so it is not the bottleneck, but the numbers
  carry that noise. The `after_repeat` control — same code, same level, run last — came back at
  2.114 rps / 432 ms p50 against 2.001 / 490 ms first time round, a ~5–12 % drift band.
- Latency is client-side full-response time, including server-side gzip and client-side
  decompression of a 5.27 MB body. Access logging is on (`serve.py --http`), identically for both.
- Windows, not the Linux container: no cgroup, no jemalloc, and RAM baselines differ from Railway's
  shape. Throughput, latency ratios and the single-core ceiling transfer; absolute values do not.
- The dataset is synthetic (the audit's 150 workers / 250 days). No production or Railway data was
  read or written.
- The timestamp parser was refined *after* these runs (see §8.1 of the audit: the fast path now
  refuses the non-canonical shapes the old `strptime` loop answered differently). Stored values are
  all 19-character canonical stamps, so nothing here is affected — `perfaudit.py proto`'s `+ both`
  arm measured 425 ms both before and after the refinement.
- `limit_concurrency=64` was never reached, so no request was refused by uvicorn; the 503 story
  belongs to the face-engine queue, which this endpoint does not touch.
